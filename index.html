Agents
Workflow

How I work with agents

I run agents as a pipeline, not a chat window. Each story gets its own git worktree from a CLI I wrote. A planner grills me on every open decision and writes a handoff, but no code. A driver builds from that handoff through role-specific subagents, including a test-first developer that writes the failing test before the code, then sends every story through three reviewers: QA, security and accessibility. A reviewer may prove a finding with a failing test but never fixes it. Agent behaviour is written once, in AGENTS.md and one manifest per agent, and every harness I use reads it through a thin stub: Claude Code, GitHub Copilot, and VS Code chat on local models.

Guardrails

Git belongs to me. Builders and reviewers never commit. One finalizer runs every check, walks the definition of done and cuts commits a reviewer can read one at a time, and it asks me before every push. Releases publish from CI with npm trusted publishing and provenance, and only when I merge a release PR. Lint, typecheck, tests and build are the definition of done for me and for agents; CI runs them on every PR and fails when published numbers or the story tracker drift from source. Nothing ships that I haven’t read.

Skills that maintain skills

I keep skills in the repo like code. They’re validated against the Agent Skills schema, audited for token cost and trigger collisions by analyzers I wrote, and third-party skills are pinned by content hash in a lockfile.

The gates

Crew & budget

The crew

  • planner

    Finds the gaps in a story and grills me in rounds, then writes the handoff.

    Starts in plan mode. Writes no code: only the handoff, and spec edits I approve.

  • driver

    Runs a story from handoff to PR: tasks to builders, every story to three reviewers.

    Never re-plans, never writes app code, never commits.

  • api-maker

    Builds from the database to the page: API, migrations, shared types, server code.

    Test first, and only the task and files the driver names.

  • tdd-dev

    Builds pages and components: a failing test first, then the code.

    Never touches a database. If the route it needs doesn’t exist, it stops and reports.

  • 3d-animator

    Owns all motion: transitions, springs, view transitions, later 3D.

    Every motion gets a reduced-motion branch.

  • qa-skeptic

    Assumes the work is broken and tries to break it against the spec.

    “The builder said the tests pass” is not proof; a command it ran and its output are. May write a failing test, never a fix.

  • owasp-hacker

    Attacks each story as a signed-in member: access, CSRF, injection, tokens.

    Local dev servers only, never a deployed host or real credentials. Proves a hole with a failing test, never a fix.

  • a11y-expert

    Checks every story against WCAG 2.2: keyboard, screen reader, zoom, motion.

    Reviews, never fixes. May write a failing axe or keyboard test.

  • pr-finalizer

    Runs every check, cuts readable commits, and writes the PR.

    The only agent that commits, and it asks before every push.

  • mentor

    Turns each finished story into a short lesson tied to its files.

    Checks every claim against the official docs. Never changes code.

Context is a budget

Context is a budget. When I measured my token usage, 93% was spent in sessions that had grown past 150k tokens, and 58% was Playwright MCP output left sitting in context. I restructured around that: a model tier per workflow step, instructions loaded only when a step runs, and compacting after every gate.

The toolkit

I’m building an open-source AI toolkit around this, designed to stay coding-standards agnostic: a project points at its own standards repo when it initializes, so teams keep their conventions and still share one workflow. Agent behaviour lives in one provider-agnostic manifest and standards live in their own files, which is what makes that split possible.

Case study

Case study: gmt, a date library that never throws

I’m a core engineer on gmt. It started as the Temporal-first standard I set at Travel Connect, and became a public library.

The problem

JavaScript’s Date is mutable, local time by default, and quietly wrong across daylight saving and time zones. gmt replaces Luxon, date-fns, Moment, Day.js, Spacetime and @internationalized/date with one API built on TC39 Temporal.

Never throws

Strings in, strings out: ISO 8601 values, never a Date. Bad input returns an empty string, null, false or an empty array, so a date bug can’t take down a page. Lint plugins for oxlint, ESLint and Biome ban Date in your own code.

The test matrix

69,479 tests across 10 time zones and 3 Node versions: 2,084,370 test runs per CI pass, in 17 locales. Every published number is derived by a script, and CI fails when the README drifts from it.

Checked against the real thing

Every week, CI compares gmt’s results with Chromium’s native Temporal in Playwright, and reports which polyfill workarounds the native engine has made removable. Kept out of the PR checks on purpose: an upstream bug must never fail a build.

Reported upstream

The bugs that hardening turned up were reported back to the source: 11 issues and pull requests to the Temporal polyfill and the TC39 proposal, each verified against the spec and Chrome.

Docs that answer back

The docs site is generated from the source, with a live playground for every function and a WebGPU time zone globe. Dox, its AI assistant, runs on free-tier models and switches to the next one inside the same request when one is rate-limited.
