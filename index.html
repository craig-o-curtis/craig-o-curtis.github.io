Agents
Workflow

How I work with agents

I run agents as a pipeline, not a chat window. Work is classified and routed through role-specific subagents: an architect that writes specs and no code, a researcher that cites primary sources, a test-first developer that must show a failing test before any fix, a coverage auditor that can only touch test files, and specialist reviewers for security, auth and UI. Agent behaviour is written once, in AGENTS.md and one manifest per agent, and every harness I use reads that source through a thin stub holding only its model and tool permissions: Claude Code, GitHub Copilot, and VS Code chat on local models. Switching tools doesn’t mean rewriting the workflow.

Guardrails

Git belongs to me. Agents commit, push or merge only on my explicit instruction, and that rule is written into every agent’s instructions. Otherwise they leave work unstaged, draft the commit message and PR description, and stop. Releases publish from CI with npm trusted publishing and provenance, and only when I merge a release PR. Lint, typecheck, tests and build are the definition of done for me and for agents; CI runs them on every PR and fails when published numbers or the story tracker drift from source. Nothing ships that I haven’t read.

Skills that maintain skills

I keep skills in the repo like code. They’re validated against the Agent Skills schema, audited for token cost and trigger collisions by analyzers I wrote, and third-party skills are pinned by content hash in a lockfile.

The gates

Crew & budget

The crew

  • architect

    Writes an implementation-ready spec: signatures, edge cases, locale and time-zone matrices.

    Writes no code.

  • researcher

    Answers design questions before anything is built.

    Primary sources only, with citations.

  • tdd-dev

    Implements in vertical slices: one failing test, the minimal fix, green, next.

    Expected values derived independently, never from the code under test. Red → green evidence required at handoff.

  • tester

    Audits coverage against priority tiers P0–P4, adding missing cases and cutting useless ones.

    May edit test files only. Two rounds with tdd-dev, then it escalates to me.

  • code-scanner

    Reviews the branch diff for security, performance and code quality.

    Every finding needs file, line and a concrete fix, and the code must be confirmed to exist before it’s reported.

  • auth-auditor

    Reviews the auth work the framework doesn’t handle: hashing, tokens, reset flows, rate limiting.

    Found and fixed 1 critical, 3 high and 2 medium issues; 30 checks passed.

  • ui-reviewer

    Reviews pages in a real browser at 375, 768 and 1280 px: layout, contrast, focus, tap targets.

    Read-only tools plus the browser.

  • feature-releaser

    Runs the release gates in strict order.

    Stops at the first failure, never fixes-and-continues. Drafts the commit and PR; commits only when I say so.

Context is a budget

Context is a budget. When I measured my token usage, 93% was spent in sessions that had grown past 150k tokens, and 58% was Playwright MCP output left sitting in context. I restructured around that: a model tier per workflow step, instructions loaded only when a step runs, and compacting after every gate.

The toolkit

I’m building an open-source AI toolkit around this, designed to stay coding-standards agnostic: a project points at its own standards repo when it initializes, so teams keep their conventions and still share one workflow. Agent behaviour lives in one provider-agnostic manifest and standards live in their own files, which is what makes that split possible.

While hardening gmt against the TC39 Temporal specification, I found real bugs in the official Temporal polyfill and in the proposal’s own reference implementation, and sent back verified issues and fixes to both. gmt already gives the correct answer for every one of them.

js-temporal/temporal-polyfill (opens in a new tab)

The community polyfill every library runs on until Temporal ships natively.

  • PR #367 (opens in a new tab)A UTC shortcut skipped a range check, so a result past the last representable instant returned instead of failing.
  • PR #368 (opens in a new tab)The Japanese calendar gave the wrong era for 1868–1872.
  • PR #369 (opens in a new tab)Non-Gregorian dates near the ends of the supported range crashed.
  • PR #370 (opens in a new tab)Counting months in Hebrew or Persian dates near the range limits threw.
  • PR #371 (opens in a new tab)A transition in the last weeks before the maximum date was missed, crashing startOfDay and hoursInDay.
  • PR #372 (opens in a new tab)The transition search started in 1847, missing Manila’s 1844 date-line crossing: hoursInDay returned 479,340 hours for a 24-hour day.
  • Issue #373 (opens in a new tab)Release request: fixes already on main hadn’t reached users, and a release would also close #341 and #347.

tc39/proposal-temporal (opens in a new tab)

The standard’s own repository, home of the reference implementation.

  • Issue #3327 (opens in a new tab)A recent change made non-Gregorian month counting wrong at ordinary dates, and throw near the range limits.
  • Issue #3328 (opens in a new tab)The time zone search bug before the maximum date, reported where the reference code lives, with the same fix.
  • Issue #3329 (opens in a new tab)An assertion assumed unreachable can be reached, in the Coptic and Ethiopian calendars’ short 13th month.
  • Issue #3330 (opens in a new tab)The 1844 date-line search bug, reported where the reference code lives, with the same fix.

Verified by

  • Expected values from the spec text, test262 and Chrome’s native Temporal, never from the polyfill
  • Every patch run on a production build of the polyfill’s main branch, with and without the change
  • The 1844 fix checked across all 418 time zones: 1,672 rows against Chrome, 6,336 transition lookups byte-identical
  • The project’s own jest and test262 suites, reported on each pull request

Not waiting on upstream

  • A probe checks once whether the installed polyfill still has each bug; if not, the workaround never runs
  • A canary (pnpm compat) reports which workarounds a new polyfill release makes removable
  • 409,552 calendar comparisons against Chrome’s native Temporal, 0 mismatches
