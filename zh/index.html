我如何与代理协作

我把代理当成流水线来用，而不是聊天窗口。每个需求都通过我自己写的 CLI 开一个独立的 git worktree。规划代理会就每一个悬而未决的决定反复追问我，然后写一份交接文档，但不写代码。执行代理根据交接文档，调度各司其职的子代理来构建，其中有一个测试先行的开发代理：先写出会失败的测试，再写代码。之后每个需求都要过三位审查者：QA、安全和无障碍。审查者可以用一个失败的测试证明问题，但从不动手修复。代理的行为只写一次，写在 AGENTS.md 和每个代理各一份的清单里；我用的每个工具都通过一个很薄的桩文件读取它：Claude Code、GitHub Copilot，以及跑在本地模型上的 VS Code chat。

护栏

Git 归我管。构建代理和审查代理从不提交。只有一个收尾代理会跑完所有检查、逐条核对完成标准、切出审查者可以逐个阅读的提交，而且每次 push 之前都会先问我。发布由 CI 完成，使用 npm 可信发布和来源证明（provenance），并且只在我合并发布 PR 时才会发布。lint、类型检查、测试和构建，对我和对代理都是同一套完成标准；CI 在每个 PR 上运行它们，一旦公开的数字或需求追踪表与源码不一致就会失败。没经过我亲自阅读的东西，一律不发布。

维护技能的技能

我像管理代码一样把 skill 放在仓库里：它们按 Agent Skills 规范校验，由我自己写的分析器审查 token 开销和触发冲突，第三方 skill 则在锁文件里按内容哈希锁定。

团队与预算

代理团队

  • planner

    找出需求里的漏洞，一轮一轮地追问我，然后写交接文档。

    从计划模式开始。不写代码：只写交接文档，以及经我批准的规格修改。

  • driver

    把一个需求从交接文档推进到 PR：任务分给构建代理，每个需求都交给三位审查者。

    从不重新规划，从不写应用代码，从不提交。

  • api-maker

    从数据库一路构建到页面：API、数据库迁移、共享类型、服务端代码。

    测试先行，并且只做执行代理指定的任务和文件。

  • tdd-dev

    构建页面和组件：先写一个失败的测试，再写代码。

    从不碰数据库。如果需要的路由不存在，就停下来报告。

  • 3d-animator

    负责所有动效：过渡、弹簧动画、视图过渡，以后还有 3D。

    每个动效都有一个“减少动态效果”的分支。

  • qa-skeptic

    先假定成果是坏的，再对照规格想方设法把它弄坏。

    “构建代理说测试通过了”不算证据；它亲自运行的命令和输出才算。可以写一个失败的测试，但从不写修复。

  • owasp-hacker

    以已登录成员的身份攻击每个需求：访问控制、CSRF、注入、令牌。

    只针对本地开发服务器，从不碰已部署的主机或真实凭据。用一个失败的测试证明漏洞，但从不写修复。

  • a11y-expert

    对照 WCAG 2.2 检查每个需求：键盘、屏幕阅读器、缩放、动效。

    只审查，从不修复。可以写一个失败的 axe 测试或键盘测试。

  • pr-finalizer

    跑完所有检查，切出易读的提交，并撰写 PR。

    唯一会提交的代理，而且每次 push 之前都会先问我。

  • mentor

    把每个完成的需求变成一节与相关文件挂钩的简短课程。

    每一条说法都对照官方文档核实。从不修改代码。

发布在 npm 上的包，以及 @northguild 旗下的项目。@northguild 是我和一位 Travel Connect 前同事共同维护的 GitHub 组织。

  • NorthGuild（在新标签页中打开）

    @northguild 的主页：在极寒北方打造的开源开发者工具。页面链接到 gmt 和 worktree，背景是伊萨菲尔德和赫尔辛基的夜空全景：星星、月亮、山峦和天际线都是真实的，只有极光是模拟的。

  • gmt（在新标签页中打开）

    “Give Me Temporal！”：一个基于 Temporal API 的 TypeScript 日期库。字符串进，严格类型出，没有 Date 的 bug。在多个时区、语言区域和 Node 版本上测试，每周与浏览器自带的 Temporal 对照检查，并附带 oxlint、ESLint 和 Biome 的 lint 规则。

  • worktree（在新标签页中打开）

    一个处理日常 Git worktree 流程的 CLI：创建、复制 .env、打开编辑器、事后清理。内置一个“与文档对话”的 AI 助手。

  • run-cv（在新标签页中打开）

    一个受大型主机启发的终端简历查看器，用 Node、React 和 Ink 构建。试试 `npx run-cv craig`。

    npx run-cv craig

  • CodeVault（在新标签页中打开）

    一个开发者知识库 SaaS，基于 Next.js、Neon Postgres、Prisma、Upstash Redis 和 Stripe 构建。

  • Mission Control（在新标签页中打开）

    一个灵活的数据库概念验证项目，向《星际迷航：下一代》致敬。用 Python FastAPI 和基于 Svelte 5 的 SvelteKit 构建，部署在 Render 上，连接 SQLite 和 Postgres 数据库。

验证方式

  • 期望值取自规范原文、test262 和 Chrome 的原生 Temporal，绝不取自 polyfill
  • 每个补丁都在 polyfill main 分支的生产构建上运行，分别带上和去掉这项改动
  • 1844 年的修复覆盖全部 418 个时区：1,672 行与 Chrome 对照，6,336 次转换查询逐字节一致
  • 每周，gmt 的全部测试都会在 Node 26、Chromium、Firefox 和 WebKit 内置的 Temporal 上运行；出现已知 bug 解释不了的失败时，会自动开一个 issue

不等上游

  • 一个探针只检查一次已安装的 polyfill 是否还有某个 bug；如果没有，对应的绕行方案就永远不会运行
  • 一个金丝雀检查（pnpm compat）报告新的 polyfill 版本让哪些绕行方案可以移除
  • 409,552 次日历比对，与 Chrome 原生 Temporal 对照，0 处不一致

案例研究

案例研究：gmt，一个从不抛异常的日期库

我是 gmt 的核心工程师。它起源于我在 Travel Connect 制定的 Temporal 优先标准，后来成为一个公开的库。

问题所在

JavaScript 的 Date 是可变的，默认使用本地时间，在夏令时和时区之间会悄无声息地出错。gmt 基于 TC39 Temporal，用一套 API 取代 Luxon、date-fns、Moment、Day.js、Spacetime 和 @internationalized/date。

从不抛异常

字符串进，字符串出：只用 ISO 8601 格式的值，从不返回 Date。输入有误时返回空字符串、null、false 或空数组，日期 bug 不会让页面崩溃。为 oxlint、ESLint 和 Biome 提供的 lint 插件，还会禁止你自己的代码使用 Date。

测试矩阵

77,745 个测试，覆盖 10 个时区，以及 3 个 Node 版本：每次 CI 运行 2,332,350 次测试，覆盖 17 种语言区域。单次运行的测试量就是最大替代库测试套件的 8 倍以上（Spacetime，8,910 个测试），而且一个都没有跳过。每个公开发布的数字都由脚本生成，README 与之不符时 CI 就会失败。

每周都有人值守

10 项检查在值守，其中 6 项按计划运行：gmt 的全部测试每周都会在 Node、Chromium、Firefox 和 WebKit 内置的 Temporal 上运行。它的 32 个变通方案各有一个探针，上游一发布修复，对应的变通方案就会自动退役。上游的 bug 绝不会让构建失败。
